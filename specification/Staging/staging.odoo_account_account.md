# odoo_account_account

## Source system
Odoo ERP (OpenERP), based on the table naming convention (`odoo_account_account`), schema naming, and the presence of Odoo-specific internal columns such as `create_uid`, `write_uid`, `create_date`, `write_date`, and JSONB-based multi-language fields.

## Functional process 
General Ledger Chart of Accounts management. This table stores the definitions of individual ledger accounts (e.g., assets, liabilities, equity, income, expenses) used in financial reporting, transaction posting, and currency handling.

## Description
One row in this table represents a single account record within the chart of accounts. As a raw landed copy in the staging layer, it preserves the exact structure of Odoo's core `account.account` model without downstream transformations. It governs whether transactions can be reconciled against the account, if it is deprecated, and its associated classification type.

## Columns

| Column | Type | Nullable | Meaning | Notes |
| :--- | :--- | :--- | :--- | :--- |
| `id` | INTEGER | false | Surrogate primary key generated by the sequence `staging.account_account_id_seq`. | Primary key assigned by Odoo during record creation. |
| `currency_id` | INTEGER | true | Foreign key referencing the specific currency configured for this account. | Null if the account uses the company's default currency. |
| `create_uid` | INTEGER | true | User ID of the user who created the account record. | References Odoo user ID. |
| `write_uid` | INTEGER | true | User ID of the user who last modified the account record. | References Odoo user ID. |
| `account_type` | VARCHAR | false | Classification category of the account (e.g., asset receivable, liability, equity, income). | Length inferred from samples — confirm against source DDL. |
| `name` | JSONB | false | Multi-language account display name. | Stored as a JSON object keyed by locale (e.g., `{"en_US": "Bank", "fr_FR": "Banque"}`). |
| `code_store` | JSONB | true | Account code storage representation, often handling multi-company or localized account codes. | Stored as JSONB. |
| `note` | TEXT | true | Free-text internal notes or description regarding the account usage. | Can contain arbitrary HTML or plain text. |
| `deprecated` | BOOLEAN | true | Soft-deprecation flag indicating if the account is active for new postings. | True means the account is closed/deprecated. |
| `reconcile` | BOOLEAN | true | Flag indicating whether journal items on this account can be reconciled (matched). | Commonly true for bank, receivable, and payable accounts. |
| `non_trade` | BOOLEAN | true | Flag distinguishing non-trade accounts from standard trade receivables/payables for financial reporting. | Boolean flag. |
| `create_date` | TIMESTAMP | true | Timestamp when the account record was created in the source system. | Stored without timezone in staging (assumed UTC). |
| `write_date` | TIMESTAMP | true | Timestamp when the account record was last modified in the source system. | Stored without timezone in staging (assumed UTC). |

## Keys

- **Primary key (inferred):** `id`
- **Foreign keys (inferred):**
  - `currency_id → staging.odoo_res_currency.id`: References the currency associated with the account.
  - `create_uid → staging.odoo_res_users.id`: References the user who created the record.
  - `write_uid → staging.odoo_res_users.id`: References the user who last updated the record.
- **Natural keys (inferred):** Not confidently inferable from the provided metadata alone (account codes may be stored inside `code_store` or handled via composite logic in Odoo).

## Caveats for downstream consumers

- Timestamps (`create_date`, `write_date`) are stored without explicit timezone information (`TIMESTAMP`); downstream models should assume UTC in accordance with standard Odoo practices.
- The `name` and `code_store` columns use `JSONB` data types to support multi-language localizations and flexible code storage; downstream consumers must extract the required keys (e.g., `name->>'en_US'`) for reporting.
- Soft-deletion or deprecation is handled via the `deprecated` boolean flag rather than row removal; historical transactions pointing to deprecated accounts remain intact.
