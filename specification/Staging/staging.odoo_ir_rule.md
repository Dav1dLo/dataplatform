# odoo_ir_rule

## Source system
This table originates from Odoo, an open-source ERP system. The naming convention `ir_rule` (Internal Record Rule) and the presence of columns like `model_id`, `domain_force`, and `perm_*` are characteristic of Odoo's internal security and access control framework.

## Functional process 
This table supports the Odoo security and access control management process. It defines record-level security rules that restrict which users can read, write, create, or delete records within specific models based on the `domain_force` filter expression.

## Description
One row represents a single security rule applied to a specific Odoo data model. It acts as a raw landed copy of the Odoo `ir.rule` system table, capturing the filter logic and permission flags that govern data visibility and modification rights across the platform.

## Columns

| Column | Type | Nullable | Meaning | Notes |
| :--- | :--- | :--- | :--- | :--- |
| id | INTEGER | false | Surrogate primary key | Sequence-generated by Odoo. |
| model_id | INTEGER | false | Foreign key to the target model | References the `ir.model` table. |
| create_uid | INTEGER | true | Creator user ID | References the `res.users` table. |
| write_uid | INTEGER | true | Last modifier user ID | References the `res.users` table. |
| name | VARCHAR | true | Rule name | Descriptive label for the security rule. |
| domain_force | TEXT | true | Filter expression | Python-based domain string used to filter records. |
| active | BOOLEAN | true | Active status | Soft-delete flag; if false, the rule is ignored. |
| perm_read | BOOLEAN | true | Read permission | If true, rule applies to read operations. |
| perm_write | BOOLEAN | true | Write permission | If true, rule applies to update operations. |
| perm_create | BOOLEAN | true | Create permission | If true, rule applies to insert operations. |
| perm_unlink | BOOLEAN | true | Delete permission | If true, rule applies to delete operations. |
| global | BOOLEAN | true | Global scope flag | If true, rule applies to all users. |
| create_date | TIMESTAMP | true | Creation timestamp | Recorded in UTC by the Odoo server. |
| write_date | TIMESTAMP | true | Last update timestamp | Recorded in UTC by the Odoo server. |

## Keys

- **Primary key (inferred):** `id`
- **Foreign keys (inferred):** 
    - `model_id` → `ir_model.id`: Links the rule to the specific data model it governs.
    - `create_uid` → `res_users.id`: Identifies the user who created the rule.
    - `write_uid` → `res_users.id`: Identifies the user who last modified the rule.
- **Natural keys (inferred):** Not confidently inferable. While `name` is descriptive, it is not guaranteed to be unique across all Odoo installations.

## Caveats for downstream consumers

- **Security Logic:** The `domain_force` column contains Python-formatted domain strings (e.g., `[('company_id', '=', user.company_id.id)]`). These cannot be executed directly in SQL and require a parser to translate into `WHERE` clauses.
- **Timestamps:** Timestamps are assumed to be in UTC, consistent with standard Odoo server configurations.
- **Soft Deletes:** The `active` column acts as a soft-delete flag; queries should generally filter by `WHERE active = TRUE` to retrieve current rules.
- **Sensitive Data:** While this table does not contain PII, it defines the security posture of the entire ERP. Access to this table should be restricted to administrative roles.
